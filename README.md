# NixCluster

"Simple" framework to manage, control and orchestrate multiple Linux devices to run parallelized programs. **Heavily** Nixed.

How it works:
1. Builders connect to RabbitMQ instance and wait for a new task.
2. Server also connects to the RabbitMQ instance.
3. User sends an URL to a Nix Flake to the server. This Flake contains two programs:
 - Generator - prepares tasks for the clients and sends them to the daemon.
 - Task template - the task itself with some empty options, which are filled by client's architecture and with custom input and configuration.
4. Server builds generator part of the Flake and runs it.
5. Generator part generates input for template part of the Flake and sends it to the server via pipes.
6. Server prepares tasks using generated inputs and sends them to builders specified by generator as Flake URL + input + architecture config.
7. Builders receive the tasks and builds them. (Using the server as a binary cache so the server can help the builders)
8. Builders run tasks, get the results from them, and send them back to the server.
9. Builders wait for the next task to run.
10. Generator receives the results, makes new tasks and merges results into the result of the whole flake.

# Task Nix Flake
```nix
{
  packages.${system} = {
    generator = derivation; # Server-side part of the task
    taskTemplate = derivation; # Builders-side part taking additional arguments as task input
  };
}
```

Framework takes the generated input, puts it raw into .nix file and runs:
```nix
packages.${system}.taskTemplate.override {
  taskInput = import ./taskInput.nix;
  builderConfig = import ./builderConfig.nix;
}
```
Input generated by generator should be a nix expression.

In reality it does not `import` this .nix file this way, but uses it as a non-flakey flake input.

Example flake:
```nix
{
  inputs = {
    nixpkgs.url = "github:nixos/nixpkgs";
    flake-parts.url = "github:hercules-ci/flake-parts";
  };

  outputs = inputs @ {flake-parts, ...}:
    flake-parts.lib.mkFlake {inherit inputs;} {
      systems = [ "x86_64-linux" "aarch64-linux" ];

      perSystem = {pkgs, ...}: {
        packages = {
          generator = pkgs.callPackage ./generator.nix {}; # Nothing weird here
          taskTempltae = pkgs.callPackage (
            {stdenv, taskInput, builderConfig, ...}:
              stdenv.mkDerivation {
                pname = "client";
                version = "1.0.0";

                src = ./.;

                BUILDER_FLAGS = builderConfig; # -march flag

                FOOBAR = taskInput.foobar; # puts the generated input
                                           # into the FOOBAR environment variable during the building
              };
          ) {};
        };
      };
    };
}
```

Generator would generate the input in the form of
```nix
{
  foobar = "123";
}
```
And then FOOBAR env var would have a value of 123 during the building

Because the entire flake is controlled by the task, the builderConfig and the taskInput can be a nix function that evaluates on the builder.
So for example the taskInput can be a function that downloads some data from the internet and the builderConfig can be dependant on the taskInput.
```nix
# taskInput.nix:
{pkgs}: # taskInput is a function taking pkgs
pkgs.fetchurl {
  url = "https://example.com/file";
  hash = "sha256-AAAA";
}

# flake.nix:
{
  # ...
  outputs.packages.${system} = {
	taskTemplate = pkgs.callPackage (
	  {stdenv, taskInput, builderConfig, ...}:
	  stdenv.mkDerivation (final: {
		# ...

		INPUT_FILE = (taskInput pkgs); # call taskInput with pkgs.
		BUILDER_FLAGS = builderConfig final.INPUT_FILE; # for example, builderConfig would generate different configs
		                                                # based on the number of lines of the input.
	  })
	) {};
  };
}
```
